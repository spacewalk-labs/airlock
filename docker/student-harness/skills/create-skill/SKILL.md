# 스킬 만들기 (create-skill)

에이전트에게 **같은 일을 두 번 이상 설명하고 있다면** 그건 스킬 후보입니다.

## 0. 먼저 판정 — 이게 스킬인가

만들기 전에 셋 중 무엇인지 정합니다. 스킬이 아닌 것을 스킬로 만들면 아무도 안 씁니다.

| 성격 | 어디에 |
|---|---|
| **매번 지켜야 하는 규칙** (예: "커밋 메시지는 한국어로") | `CLAUDE.md` — 스킬 아님 |
| **어쩌다 한 번, 상황이 오면 밟는 절차** (예: "문서를 발행한다") | **스킬** |
| **명령 한 줄** (예: `npm run build`) | 그냥 명령. 스킬로 감싸지 않습니다 |

핵심 질문 하나: **언제 꺼내 쓸지 설명할 수 있나요?** 못 하면 스킬이 아니라 규칙입니다.

## 1. 어디에 두나

- **이 박스에서만 쓰는 것** → `~/.claude/skills/<이름>/SKILL.md`
- **레포에 붙는 것**(그 프로젝트를 아는 사람에게만 의미 있는 절차) → `<레포>/.claude/skills/<이름>/SKILL.md`

🔴 **사본을 만들지 마세요.** 같은 스킬이 두 곳에 있으면 반드시 한쪽이 낡습니다.
한 곳에 두고 나머지는 심링크입니다.

## 2. 구성

```
skills/<이름>/
  SKILL.md          # 필수. 이것만 있어도 됩니다
  references/*.md   # 길어지면 분리 — 본문에서 링크
  scripts/*.py      # 실물 스크립트. 설명 대신 실행되는 것
```

**본문은 500줄을 넘기지 마세요.** 넘으면 `references/` 로 가릅니다 —
에이전트가 스킬을 고를 때는 본문을 다 읽지 않습니다.

## 3. description 이 가장 중요합니다

에이전트는 **description 만 보고** 이 스킬을 꺼낼지 정합니다. 본문은 그다음입니다.

- ✅ **언제 쓰는지**를 씁니다: "PDF에서 표를 뽑아 CSV로 만들 때 쓴다"
- ❌ 무엇인지만 쓰지 않습니다: "PDF 처리 도구"
- 사용자가 실제로 쓸 **낱말**을 넣습니다. "표 추출"이라고 말할 사람에게 "테이블 파싱"은 안 걸립니다.

## 4. 본문 스타일

- **절차·명령·계약만** 담습니다. 배경 설명·역사는 빼거나 `references/` 로.
- **"절대 하지 마"는 문서에 적기보다 막는 편이 낫습니다** — 지침 텍스트는 지켜 주기를 바라는 것이고,
  `settings.json` 의 `deny` 는 실행 자체를 막습니다.
- 강한 단정("항상", "반드시", "절대")은 **실제로 재 보고** 씁니다. 안 재고 쓴 단정은
  다음 사람이 그대로 믿고 틀립니다.

## 5. 절차

1. 위 0번으로 스킬인지 판정.
2. `skills/<이름>/SKILL.md` 를 만들고 frontmatter(`name`·`description`)를 채웁니다.
3. **한 번 실제로 시켜 봅니다** — 에이전트에게 그 일을 시키고, 스킬을 꺼내 쓰는지 봅니다.
   안 꺼내면 description 문제입니다.
4. 안 꺼내 쓰는 스킬은 **지웁니다.** 쌓인 스킬은 고르기를 어렵게 만들 뿐입니다.

## 6. 확인

- `name` 이 폴더 이름과 같은가
- `description` 만 읽고 **언제 쓸지** 알 수 있는가
- 본문에 **실행되는 명령**이 있는가 (설명만 있으면 대개 규칙이지 스킬이 아님)
- 시켜 봤을 때 실제로 꺼내 쓰는가
