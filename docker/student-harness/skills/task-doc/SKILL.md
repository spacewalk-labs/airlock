# 태스크 문서 먼저 (task-doc)

LLM은 사람과 닮아, **계획을 세우고 검토한 뒤** 일하면 결과가 확연히 좋아집니다. "바로 코딩"이 아니라
**문서 → 리뷰 → 재작성 → 실행** 순서로 갑니다. 계획이 곧 **첫 번째 검증**입니다.

## 언제

- 작지 않은 작업, 여러 파일에 걸치는 변경, **되돌리기 어려운** 일.
- (아주 작은 일은 한두 줄 계획으로 충분 — 이 절차는 생략.)

## 순서

1. **태스크 문서 작성** — 다음을 한 페이지로:
   - **목표**(무엇을·왜) · **범위**(할 것/안 할 것) · **접근**(어떻게) · **검증 계획**(어떻게 확인) · **위험/가정**
2. **리뷰** — 스스로 또는 다른 에이전트로 점검: **빠진 경우 · 잘못된 가정 · 불필요한 복잡성**.
   중요하면 [`self-verify`](../self-verify/SKILL.md)로 반박 검증.
3. **재작성** — 리뷰에서 나온 것을 반영해 문서를 고칩니다.
4. **실행** — 그제야 코딩·작업. 진행 중 새 사실이 나오면 **문서를 갱신**(계획은 살아 있는 첫 검증물).

## 어디에

- 프로젝트의 `docs/` 나 이슈/PR 설명, 또는 [`worklog`](../worklog/SKILL.md) 앞에 붙입니다.
  정해진 곳이 없으면 사용자에게 한 번 확인.

## 주의

- 문서는 **짧고 구체적으로**. 계획을 위한 계획이 되지 않게.
- 목표·제약이 분명하면 상위 모델은 중간을 알아서 채웁니다 — 세세한 지시로 도배하지 마세요.

## 출력

```
태스크 문서: <위치> (목표·범위·접근·검증·위험)
리뷰 반영: … → 실행 시작
```
